# bcgen-lang v0.2.0 — HIR to LSB, the Dynamic Profile

**The foundation.** v0.2.0 turns the scaffold into a working compiler from
HIR (spec v2, hir-lang 0.3) to LSB (format version 1, bytecode-lang 0.2):
hand it a resolved unit and it returns an LSB module that bvm-lang
2.0.0-alpha.1 loads and runs. It compiles the **dynamic profile**, every
value an LSB `dyn`, which is what Mox and the other dynamic languages run
under, and it is the piece LexerSketch decision D19 calls for: HIR to LSB
directly, so the Demo, the REPL, and hybrid bytecode units run on bvm-lang.

## What is bcgen-lang?

The bridge from a forged language's meaning to code the VM runs. It owns the
HIR to LSB translation: register allocation over LSB's register windows,
closure conversion, pattern compilation, exception and `finally` lowering by
LSB's canonical scheme, and debug information mapping every instruction back
to its HIR origin. It does not parse, resolve, type-check, or execute. It is
an LXRT-tier crate depending on hir-lang, bytecode-lang, and intern-lang.

## What's new in 0.2.0

### The Tier-1 path

```rust
use bvm_lang::{Host, Program, Value, Vm};
use hir_lang::{Builder, Name, OpKind};
use intern_lang::Interner;

let mut names = Interner::new();
let mut b = Builder::new();
let (p, n) = b.local_param(Name::new(names.intern("n")));
let un = b.use_binder(n);
let one = b.int(1);
let next = b.op(OpKind::Add, &[un, one]);
let body = b.block(&[], Some(next));
let inc = b.func(Name::new(names.intern("inc")), &[p], body);
let root = b.module(None, &[inc]);
let hir = b.finish(root)?;

let out = bcgen_lang::compile(&hir, &names)?;
let program = Program::load(out.into_module(), &Host::new())?;
assert_eq!(Vm::new(&program).run_export("inc", &[Value::Int(41)])?, Value::Int(42));
# Ok::<(), Box<dyn std::error::Error>>(())
```

`Compiler` adds `Options` (PHP or shared-reference arrays, PHP key coercion,
whether the module body is the start function or the entry, hooks bound to
host functions, an instruction budget) and a `Locate` for line tables
(`LineIndex` for one file).

### What compiles

- **Functions** with positional-only, normal, rest, named-only, and
  named-rest parameters, defaults evaluated per call (seeing the earlier
  parameters) or once, by-reference parameters. A call of a known function
  is arranged at compile time and made with LSB's direct `call` and a
  presence mask; every function *value* takes an argument packet, so a
  dynamic call (`dcall`, whose arity LSB checks exactly) works with any
  arguments. Both paths bind by the same rules and raise the same errors at
  the callee.
- **Closures** with explicit, implicit, and recursive captures, by value or
  through cells; shared variables live in cells, the rest in registers that
  are reused when their scope closes.
- **Control flow**: `if`, labeled blocks, the loop primitive with its step,
  labeled `break`/`continue`, `return`; `match` by a sequential decision
  procedure over literal, binding, identifier, range, tuple, slice, record,
  or, and type-test patterns with guards; let-else.
- **Operations**: every OPS operation on dynamic values under its policy,
  `promote` included; conversions and casts by dynamic kind.
- **PHP arrays**: values (copied on transfer with LSB's O(1) copy-on-write
  `dup`, separated on nested writes, created on write through `null`), with
  PHP's key coercion through an emitted helper; or shared references.
- **Exceptions**: `throw`, `try`/`catch`/`finally` by LSB §4.3's canonical
  lowering (one `finally` copy, a completion kind and value, a dispatch;
  jumps out of `finally` override the pending completion), and `defer`.
- **Modules**: globals, constants, statics, `global` aliases, nested module
  bodies, the module body (as the start function, or the entry function).
- **Host calls** through LSB imports, **hooks** bound to host functions, and
  named intrinsics for concatenation, length, truthiness, kind, and
  `foreach` iteration.
- **Debug information**: the HIR node of every instruction
  (`Compiled::origin`), line tables through `Locate`, debug locals.

Not yet, each a precise `Unsupported` error: coroutines, classes, declared
records and sums, and typed fast paths (0.5); references into array slots,
variable variables, host functions as values (LSB features that do not
exist).

### How it is checked

- **The differential oracle.** `tests/common/reference.rs` is a reference
  HIR interpreter written independently of the compiler (PHP arrays as real
  deep copies, OPS arithmetic in `i128` and `f64`, control flow as Rust
  results). `tests/common/progs.rs` generates random well-formed programs
  with hir-lang's `Builder`. Results, printed output, error kinds, and error
  locations (the raising HIR node) must match bvm-lang's, under both array
  profiles. Over a million programs were run before release; it found ten
  compiler defects on the way, each fixed and kept as a regression seed. Mutation
  checks confirm it fails when the array copy is removed, two `finally`
  dispatch targets are swapped, `floor_mod` is compiled as `rem`, or PHP key
  coercion is broken.
- **Properties**: every module loads in bvm-lang and round-trips through the
  LSB encoding; every instruction maps to a node of the unit; line rows are
  increasing; compilation is deterministic across clones and threads.
- **End to end**: a Mox program, lowered by hand, resolved by resolve-lang,
  compiled, and run on bvm-lang with a printing host function.
- **Hostile input**: 100,000-deep expressions compile on a 512 KiB stack (the
  generator is an explicit task stack); the instruction budget holds.

## Performance

Release build on the development machine (Windows 11), criterion medians from
`benches/bench.rs`. Compile figures are library-only (HIR in memory to an LSB
module, no encoding); run figures are bvm-lang 2.0.0-alpha.1 executing the
compiled module (VM instance creation included).

| Benchmark | Result |
|---|---|
| Compile, synthetic unit, 152k HIR nodes | 23 ms (6.6 M nodes/s) |
| Compile, synthetic unit, 532k HIR nodes | 103 ms (5.2 M nodes/s) |
| Compile, synthetic unit, 1.52M HIR nodes | 354 ms (4.3 M nodes/s) |
| `fib(25)`, direct calls | 8.6 ms |
| Counting loop, 1M iterations | 10.7 ms |
| PHP array: 100k appends, then 100k indexed reads | 13.0 ms |
| The same plus 100k nested writes `g[i % 64][] = i` | 371 ms |

"Nodes" counts items, expressions, statements, patterns, paths, and
parameters. Compile time is linear: `tests/scaling.rs` measures 150 to 170 ns
per node from 146k to 2.3M nodes (the criterion spread above is allocator
noise around that). The last row is the cost of PHP nested-write separation:
LSB cannot ask whether an inner array is shared, so every nested write copies
the inner array's store while the old copy is uncollected (about 28 times the
plain-append case here). An LSB instruction that separates only when shared
is requested from the spec owners.

## For the LSB and HIR spec owners

Mismatches and gaps met while building this, to fold into the specs:

1. **No "separate if shared" for maps (LSB).** PHP value semantics need a
   nested write to copy an inner array only when another array shares it.
   LSB offers `dup` (always a new header) and copy-on-write stores, but no
   way to ask whether a store is shared, so bcgen separates on every nested
   write: correct, but each nested write into a large inner array costs a
   store copy while the old header is uncollected. Request: a
   `dset_index_separate` (or `map_unshare`) instruction that copies only when
   the store's reference count is above one.
2. **No references to map slots (LSB).** `f(&$a[0])` to a by-reference
   parameter and `$x = &$a[0]` cannot be expressed; only whole variables can
   be shared (through cells). bcgen reports `Unsupported::RefPlace`.
3. **By-reference decisions for dynamic calls (HIR §8.1, LSB).** HIR says the
   callee decides, at run time for dynamic calls, whether a place argument is
   taken by reference. LSB has no per-call way to ask a callee's parameter
   modes before the arguments are sent, so bcgen passes a shared variable's
   cell and lets the callee unwrap it: by-reference works, but a by-value
   parameter reads the variable when bound (after every argument), not when
   the argument was evaluated, and an element place is passed by value.
4. **Variadic dynamic calls (LSB §10 Q3).** `dcall` requires exact arity, so
   every function value takes an argument packet (two `dyn` parameters,
   unpacked by a prologue): an allocation per dynamic call. A `variadic` flag
   on functions (rest parameter as an array) would remove it.
5. **Imports have a fixed arity (LSB).** A host function used as a value has
   no arity to import with (`Unsupported::ExternValue`), and spread or named
   arguments cannot reach one.
6. **`match` with no matching arm (HIR §8.4).** The spec says "first matching
   arm wins" but not what happens when none does. bcgen evaluates to `nil`;
   lowerings that need an error (PHP `match`) must add a final arm. Please
   state it in the spec.
7. **Compound assignment order (HIR §8.2).** "target is evaluated once"
   leaves open when the old value is read relative to the right-hand side.
   bcgen reads it before evaluating the value, and resolves a variable root
   when writing (after the value). Please state it.
8. **`promote` on `abs` (OPS, LSB).** `abs` with `promote` is valid HIR but
   there is no dynamic `abs` instruction; bcgen emits the `i64` path with an
   explicit `MIN` check. A `dabs` would be one dispatch.
9. **NaN sign (OPS).** Dynamic floats hold one canonical NaN, so
   `total_cmp` and bit casts of a NaN see the positive NaN whatever produced
   it; worth stating in OPS for the dynamic domain.
